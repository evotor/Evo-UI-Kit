# Стили узлов, вынесенных сторонней библиотекой из компонента, адресуются классом-маркером

- Статус: accepted
- Класс: architecture
- Тикет: NLMA-7175
- Вытесняет: нет

## Задача

Часть компонентов кита оборачивает сторонние библиотеки, которые умеют переносить свои
всплывающие узлы в произвольный контейнер: `ng-select` делает это по `appendTo`, и то же самое
рано или поздно понадобится любому оверлею.
После переноса узел перестаёт быть потомком элемента компонента, и правила, написанные под
вложенностью `evo-<компонент> { ... }`, на него не попадают: панель, календарь или подсказка
рисуются дефолтными стилями библиотеки.

Поднять правила на верхний уровень мало: у таких компонентов `ViewEncapsulation.None`, то есть
любое верхнеуровневое правило становится глобальным для всей страницы потребителя.
Вопрос в том, чем отбирать вынесенный узел, чтобы не захватить чужие.

## Решение

Компонент вешает на элемент библиотеки статический класс-маркер вида `evo-<компонент>-<роль>`
(в `evo-autocomplete` - `evo-autocomplete-panel`), а правила вынесенного узла живут на верхнем
уровне и адресуются этим маркером двумя плечами:

- `.<маркер>.<класс-узла>` - когда узел вынесен и маркер стоит на нём самом;
- `.<маркер> .<класс-узла>` - когда узел остался внутри и маркер работает как класс предка.

Селектор с голым именем стороннего пакета (`.ng-dropdown-panel`, `.flatpickr-calendar`) на верхнем
уровне не пишется: имя принадлежит не киту, и потребитель вправе использовать тот же пакет напрямую.

Проброс маркера обеспечивает сама библиотека, и это контракт с ней, а не деталь реализации:
`ng-select` копирует на вынесенную панель статический атрибут `class` элемента `<ng-select>`.
Такой контракт закрепляется спекой, иначе апгрейд пакета уронит стили молча.

Специфичность правил подбирается так, чтобы ни одно из них не совпало по весу с собственным CSS
библиотеки: при равенстве победитель определяется порядком вставки `<style>` в `head`, то есть
порядком первой отрисовки компонентов в приложении потребителя, а это недетерминированно.

Переменные оформления объявляются **только** на вынесенном узле. Внутри компонента узел получает их
наследованием от элемента `evo-<компонент>`, и собственное объявление на нём убило бы публичную
кастомизацию через `style` на компоненте: объявление на элементе всегда бьёт унаследованное значение.

## Последствия

- Маркер становится публичным API: он попадает в `MIGRATION.md` вместе с требованиями к контейнеру.
- Переопределение переменных вынесенного узла требует от потребителя селектора не слабее собственного
  селектора кита - обычно это отбор по контейнеру, в который узел вынесен.
- Прецедент `evo-datepicker`, где стили `.flatpickr-*` лежат на верхнем уровне без маркера, этим
  решением не легализуется: там это безопасно только потому, что flatpickr используется одним китом.
